# Coordinator resume: local CLI and cloud reminders

The local CLI watchdog is the reliable push path: it can start a configured Claude Code or Codex CLI when a lane needs attention and no coordinator is active. It does not reopen Claude Desktop or ChatGPT, recover their chats, start OMP, or guarantee task completion. The PC must be awake, the user logged on, OMP available, and the CLI already installed, authenticated and configured with its approved local MCP connection. Native permission prompts, quotas and network failures can still stop progress.

Cloud reminders are best-effort. A fresh cloud session has no chat memory, may be unable to reach local PCs or read a local handoff file, and may stall at permission prompts. POTS supplies no cloud connector, account integration, credentials or scheduling API. Generating text does not create a recurring task.

## Setup and handoff

A plain `pots install` or `pots upgrade` turns CLI resume on by itself when it finds Claude Code or Codex (Claude Code first) on the `PATH`, and creates the handoff file for you. With none found it stays off and `pots doctor` says no command-line program was selected for wake-ups; a cloud-only setup (`--resume-cli none` with a cloud choice) is shown as your choice, not as a missing program. `pots install --no-coordinator-wakeups` (or the same flag on `setup-auto`) keeps it off: it removes an existing scheduled task (when old wake-up files cannot be checked as Setup's own, it leaves the task alone and says so) and forgets the saved wake-up settings (which handoff file to read, check interval, cloud task choice; the handoff file itself is not deleted), so turning wake-ups on again with `--coordinator-wakeups` starts from the standard settings; it keeps everything else, skips the self-test, and `pots status` says wake-ups are off by your choice and names the command to turn them on again. On `setup-auto`, `--no-coordinator-wakeups` cannot be combined with `--resume-cli`, `--resume-cloud`, `--handoff-file` or any other resume option: that is refused, so off always means off. The choice is stored once: a session that is saved later and a later plain `pots install` keep it. A session that is open while you run it keeps its old choice until it is closed, and the install says so; the install still remembers "off" itself (one small file, `coordinator-resume/control/wakeups-off`), so a later plain install keeps wake-ups off and the open session follows the first install after it closes. To turn wake-ups on again, run `pots install --coordinator-wakeups` (or the same flag on `setup-auto`): it removes that file, sets the scheduled task up again and runs the self-test. A session that is open at that moment follows the first install after it closes; until then the install remembers "on" in a second small file (`coordinator-resume/control/wakeups-on`), which it removes once every session agrees. `--coordinator-wakeups` and `--no-coordinator-wakeups` together are refused, and `pots uninstall` works after either choice. The `setup-auto` command line offers independent Claude / ChatGPT / both selections for CLI resume and cloud reminder text; cloud text defaults to off. ChatGPT CLI resume means Codex CLI, not ChatGPT desktop. Choose only clients included in the installation's coordinator-client selection (both, unless `--clients` limits it). Keep one directing assistant and the existing controller capability/handoff rules; selecting both never grants two directors independent authority.

The handoff file is `coordinator-resume/handoff.md` unless you pass `--handoff-file`. Keep it current with approved next steps, lane/connection names, result locations, completion criteria, and unresolved outcomes. Do not put passwords, tokens or controller-key contents in it. A file path is not cloud reachability: if a cloud session cannot read the approved handoff through its authorized tools, it must stop and explain the missing route.

The installer ships a resume prompt file. The launched coordinator must read the handoff, refresh `bridge_coordinator_heartbeat` for each lane it directs, call `bridge_lanes_status`, and run the check-and-kickstart cycle. Read every attention lane's receipt/result, safely close finished lane windows when appropriate, and queue only the next approved step. A stopped lane is continued with `pots lane restore <name>`, or, if its OMP window is still open, by looking at it with `/bridge status` and then `/bridge enable` there; never queue a new step on it and never close its window. Receipts that are failed, malformed, aborted or expired need the owner; never replay or requeue them automatically. A fresh session must not infer approval or completed work from missing chat history.

CLI registration and login remain the owner's responsibility. Keep write approvals enabled. The helper does not pass credentials on the command line, perform login, bypass tool approvals, or acquire controller authority. A headless CLI can wait or fail at an approval prompt; that is not success.

## Local setup, dry-run and disable

Resume is set up with the command line:

```powershell
node bin/bridge.mjs setup-auto --session "C:\Sessions\saved.jsonl" --root "C:\Private\POTS" --clients both --resume-cli claude --resume-cloud both --handoff-file "C:\Projects\Example\handoff.md" --resume-dry-run
```

Use `--resume-cli chatgpt` for Codex or `both` for both candidates; `none` disables that mode. Optional `--claude-executable` and `--codex-executable` select absolute executable paths rather than PATH discovery. Claude accepts either `--claude-session <session-id>` (passed as `--resume`) or `--claude-continue`; never both. These options select an existing CLI session, not a Desktop/cloud conversation. Session IDs contain only letters, digits, underscore and hyphen.

Detection defaults to 2000 ms. Set `--resume-poll-ms 1000` (or `coordinatorResume.pollMs` in the setup-helper request) for 1-second polling; integers from 1000 through 15000 are accepted. The generated `config.json` records `pollMs`. Reconfigure by running `setup-auto` again rather than editing a hash-owned config by hand. A missing `pollMs` in an older configuration uses the new 2000 ms default. Faster polling performs local file/status checks only: no model, CLI, token probe or provider request is used to detect attention.

The installer creates `coordinator-resume/config.json`, `resume-prompt.txt`, `Disable-Resume.cmd`, `Run-Resume.vbs`, selected `claude-cloud-task.txt` / `chatgpt-cloud-task.txt`, `handoff.md` (only if missing; it is yours afterwards and is never replaced or hashed) and a hash ownership record. Each generated file is written to a temporary file and renamed, so a power cut never leaves half a file. If an install is cut off after these files were written but before the uninstall list was, `pots install` run again recognises the folder as its own when every file in its ownership record is there with its recorded hash, and repairs the list; one changed or missing file leaves the folder as it is. CLI mode also registers one Windows scheduled task named after the install, run as you without elevation and without a window. It starts at log-in and then every 5 minutes; a copy that is already running is never doubled, so a closed or crashed watchdog is back within 5 minutes, also after a restart. A lock left by a crash or a restart is taken over when its recorded process is gone, or when that process number is alive again but the watchdog's own log (written every poll) has been silent for twice the time `pots doctor` allows (60 seconds or 12 polls, whichever is longer) and is still silent one more poll later. Windows hands the same process number to another program after a restart, and the PC's start time is no proof (Fast Startup keeps it running through a shutdown, and a clock change shifts it), so the log is the proof. A lock whose watchdog keeps writing its log, or has only just started and has not written yet, is never taken. A lock with no readable owner note is cleared once it is older than 5 minutes. If `pots doctor` still says the watchdog stopped and names its lock folder, delete that folder (only while no watchdog is running) and run `pots install` again. Setup starts the task right away, so nothing waits for the next log-in. Earlier versions put a `.cmd` file in the Startup folder instead; the next install removes that file when it is unchanged and uses the task. To start or inspect the helper by hand, run the installed runtime's `bin/coordinator-resume.mjs` with the generated config.

The same repair also works after two cut-off installs in a row: a file that is not what the ownership record lists, but is exactly what this version would write, counts as Setup's. The uninstall list is saved the same way as the wake-up files (temporary file, then rename). A list that was cut off anyway is treated as missing, so `pots install` rewrites it; until then `pots uninstall` says to run `pots install` first.

```powershell
node "C:\Private\POTS\runtime\<installed-runtime>\bin\coordinator-resume.mjs" --config "C:\Private\POTS\coordinator-resume\config.json" --once --dry-run
```

Use the `runtimeFolder` returned by Setup in place of `<installed-runtime>`. `--dry-run` creates no child processes, including no token probe. It reads real configured lane state, records the decision and consumes the same rate quota as a launch; `--once` exits after one cycle. A quiet lane does not trigger a resume. Remove `--once` for continuous polling, but retain `--dry-run` until the handoff and MCP configuration have been checked. Configured `dryRun:true` cannot be overridden by omitting the CLI flag; run `setup-auto` again without `--resume-dry-run` to request live mode.

Run `Disable-Resume.cmd` to stop future launches; it creates a disable marker with text in it, exclusively, preserving any existing file. The watchdog notices it within one configured poll (2 seconds by default), plus in-progress bounded local checks, and exits. Disabling never kills an already launched coordinator or active OMP work. When `pots install` or `pots upgrade` needs to restart the watchdog on new code, it writes its own empty marker, waits for the watchdog to exit, removes only that empty marker, registers the task and starts the watchdog again. A marker with text in it is yours: Setup never removes it, `pots doctor` says so, and wake-ups stay off until you delete `coordinator-resume/control/disabled` and run `pots install`. `pots install` and `pots upgrade` say so as well, run no self-test and finish with exit code 0.

Uninstall pauses this helper before removal and waits for its owned lock to close; it does not kill a PID or unrelated process. It then deletes the scheduled task, but only a task that still carries this install's marker in its description. It reports the task gone only when Windows confirmed the delete or showed that the task does not exist; if Task Scheduler cannot be asked, nothing is removed and it says what to check. Stopping a task does not stop a watchdog that is already running, which is why the pause marker comes first. A blocked uninstall takes its own pause away again; a pause you made with Disable-Resume is never touched. Removal verifies installed file hashes. Modified/unowned internal files block removal rather than being deleted. Node, OMP, project files, a handoff file you pointed to elsewhere with `--handoff-file`, client accounts and manually created cloud tasks are not removed. The standard `coordinator-resume/handoff.md` is inside the install folder: a normal removal keeps it in the recovery copy, and a `--purge` first copies it next to the install folder as `Pi on the Side handoff.md` (a number is added when that name is taken, an existing file is never overwritten) and names the copy in the result as `handoffKept`. Cancel the cloud tasks separately.

`pots uninstall` also accepts what an interrupted update, install or setup of Pi on the Side itself left behind: `staging` folders of an update (only release file names), a `runtime\managed-...` folder an interrupted install moved aside, and `<name>.<uuid>.tmp` leftovers of the files Setup writes (including `local-setup.json`, `uninstall-record.json`, `current.json` and a lane's `launch-settings.json`). Any other file inside them still stops removal. A folder or a link named `disabled` in `coordinator-resume/control` does not stop removal; a link is removed itself, never what it points to. A purge copies the handoff file before it removes anything, including the scheduled task; if the copy cannot be made, nothing is removed. The copy gets the access rules of the folder it is made in (the folder that holds the install folder), so anyone who can open that folder can read it.

## Check it: `pots doctor`

`pots doctor` lists each part in plain words: wake-ups switched on, a Claude Code or Codex program found, the handoff file present, the scheduled task present, the watchdog alive (it rewrites its log every poll, so a log older than 30 seconds or 6 polls, whichever is longer, means it stopped) whether the last start failed, and whether the watchdog's own safety check keeps failing. When you chose `--no-coordinator-wakeups` it says wake-ups are off by your choice, names `pots install --coordinator-wakeups` as the way to turn them on again, and runs no self-test. It then runs the self-test: a throwaway lane in a temporary folder finishes a plan and goes idle; the real lane watcher must show IDLE within 15 seconds, or within the lane's own quiet time plus one poll plus 5 seconds when that is longer (`pots install` and `pots upgrade` use the lane's own watcher timing, `pots doctor` the defaults of 5 and 8 seconds), and the real lane status and the real watchdog decision (in dry-run, so no program starts) must choose to start a coordinator. The seconds are measured and printed as PASS or FAIL, then the temporary folder is deleted; if it cannot be deleted the test says FAIL and names it. Not proven: that the Claude Code or Codex program really opens, because that happens only for a real lane. `pots install` and `pots upgrade` run the same self-test at the end. Every failure is also appended to `pots.log` (two files of at most 64 KiB) in the install folder, and `pots status` shows `Wake-ups: NOT WORKING` with the first reason.

## Heartbeat and launch conditions

`bridge_lanes_status` remains read-only. The separate `bridge_coordinator_heartbeat` tool refreshes one setup's `control/coordinator-active.json` through the current controller capability. It accepts no path, credentials or task content. Named-connection mode requires an explicit `connection`; repeat for every lane directed by this coordinator.

Refresh at the start of each cycle and at least every 120 seconds during long coordinator processing. The marker is fresh for 180 seconds. This is liveness evidence, not a lease, identity check or authority transfer. A crashed coordinator becomes eligible only after its marker expires. A marker dated up to 5 minutes ahead (a clock set back a little) counts as now. Malformed, dated further ahead, linked or unreadable state suppresses launches instead of guessing; `pots doctor` then names the marker file to delete.

The watchdog reads the same bounded lane summaries as MCP, sourced from lane-events, receipts and diagnostics. It acts on finished-idle lanes, failed or malformed plans, unexpectedly gone lanes and a stopped lane (a task was running and no bridge is running it any more: OMP closed or crashed, or its bridge stopped), only when no relevant coordinator marker is fresh. For a stopped lane the generated prompt tells the coordinator to continue it with `pots lane restore <name>` (or, if its window is still open, `/bridge status` then `/bridge enable` there), and not to queue a new step on it or close its window. It never changes a receipt, replays a failed plan, submits a bridge plan itself, or decides that a task succeeded.

The watchdog polls every 2 seconds by default; 1-second polling is configurable. This is a detection cadence, not a guarantee that the director finishes its response within that time. Persistent global limits remain a 120-second cooldown and at most six attempts per hour; each lane has a 300-second cooldown and at most three attempts per hour. Attempts include failed launches and dry-runs, reserved before starting a child. One coordinator launches per tick; Claude is preferred if both are configured. Select one client when you want a specific director rather than relying on that ordering.

`coordinator-resume/control` holds the single-instance `watchdog.lock`, persistent rate state, a bounded 128-record launch log and disable marker. Logs contain only fixed outcomes and bounded identifiers/timestamps, never prompts, handoff contents, raw errors or credentials. A failed or ambiguous launch is not task success. A lock left by a crash is taken over only under the rule above; a lock held by a running process is never taken.

An existing fresh marker on any monitored lane suppresses all new coordinator launches. The helper requires a non-elevated Windows medium-integrity token. It resolves configured/PATH native executables and recognized standard npm CLI package entrypoints without executing arbitrary `.cmd` or `.ps1` text; unfamiliar shims fail closed.

## Duplicate events and superseded wake-ups

`bridge_lanes_status` adds `eventId`: a SHA-256 identity of the actionable receipt/event facts, or `null` when no event requires attention. Refreshed diagnostic timestamps do not create a new event. A durable lane/event reservation suppresses unchanged attention even after cooldown, helper restart or an intervening result. Only reserved events appear in the launch prompt's action allowlist; all other lanes are read-only in that invocation. Failed launches, dry-runs and a barrier that closes after reservation conservatively consume the event; automatic retry is not authorized.

`coordinator-resume/control/state.json` is version 2 and contains the current numeric `cycleId`, rate histories and event ledger. Each durable launch reservation increases the cycle ID. Generated instructions bind that ID and the authority file path into every subsequent wake-up. Before reading a handoff, acting or scheduling, the coordinator must compare the bound ID with the file; a different/missing/unreadable/malformed ID exits with exactly `POTS resume superseded or unavailable.` and does no work or rearming. A reminder must never adopt a newer ID.

Schedule exactly one next wake-up; before scheduling, list and delete other pending ones. Stop scheduling and remove pending reminders when no work runs. If the client cannot list/cancel reminders or read the local authority, report that limitation instead of claiming stale wake-ups were cleared. POTS does not control external scheduler queues; this is a coordinator contract, not an atomic transaction with a provider scheduler. Existing pre-upgrade reminders do not contain this guard and must be cancelled manually at cutover.

The ledger is bounded to 512 distinct event identities and 64 lane keys. When it is full, the oldest identities are dropped first, never one that is still current, so a finished event is not launched twice and the watchdog never stops because the ledger filled up. Malformed state suppresses launches as `safety`; `pots status` and `pots doctor` then show a failing row with the one next step. Upgrading version-1 state preserves quota and baselines currently actionable events without launching them, because their prior emission cannot be established. Keep the version-2 authority/ledger across helper restarts; restoring an old copy can reuse cycle IDs and is not a safe rollback.


## Cloud reminder helper

For each selected client, `setup-auto` generates exact recurring-task instructions and a fresh-session prompt. Review the generated text, then create the recurring task yourself in the client's supported UI:

- Claude: use its scheduled-task/routine facility if available for the account and client.
- ChatGPT: use ChatGPT Tasks if available for the account and client.

Use the generated recurrence and full prompt, not a reference to this chat. Confirm in the client that the task exists, the recurrence is correct, and its session can read the handoff and call the authorized bridge tools. If those capabilities are unavailable, report the limitation and use local CLI mode instead. Generated text cannot unlock an inaccessible computer or answer approval prompts. The cycle rule above applies only to text generated together with a local watchdog; with `--resume-cli none` there is no watchdog and no cycle file, so the cloud text has no such rule.

When disabling or uninstalling POTS, cancel any manually created cloud task in that client's own UI. POTS cannot discover or remove it without account access and does not claim to do so.

## Privacy and qualification

The resume prompt contains configured local file paths but not file contents; the CLI and provider will see the prompt and any handoff/results the coordinator reads. Protect the install and handoff, review generated cloud text before uploading it, and use the client's privacy controls. Launch/heartbeat records must not be treated as a task-success receipt.

Automated source tests use disposable fixtures; they do not prove assistant permissions or external scheduling. See [verification](verification.md) for measured latency, CPU and limits, and [coordinator wake-ups](coordinator-wakeups.md) for the same-chat protocol.
