# Advanced operations and recovery

This page covers detailed checks when a saved OMP session or local bridge setup needs review. Start with the [quickstart](release-quickstart.md) for ordinary setup and status checks.

## Activation and duplicate prevention

Do not stop an active OMP session only to test the bridge. `start "<state-folder>"` without `--confirm-offline` previews the exact launch. Before starting, let `setup` derive and `start` recheck the saved header and exact project folder; verify no OMP process/window is writing that session and check private state permissions. Use `--confirm-offline` only after all writers are safely stopped. The bridge resumes the same saved session in the foreground with `--no-extensions` and one explicit bridge extension, so normal extension discovery does not load a duplicate; discovered extensions are also not loaded for that run. Preserve OMP provider/advisor/escalation settings and do not add the bridge extension to a global discovery root.

The internal lock prevents a second bridge supervisor sharing its state root/session; `start` also refuses while the lock exists and never steals it. It cannot detect a separate OMP writer without this extension, a second private state root for the same session, or an opaque process command line. Neither the preview nor the confirmation proves these absent. If process/session ownership is ambiguous, return to the existing owner window and stop. No automatic process killing, keyboard injection, or duplicate session fallback exists.

## Status and troubleshooting

Use `node bin/bridge.mjs status "<state-folder>"`. No receipt means queued, not running. Receipts are durable observations, not a heartbeat; an old submitted receipt cannot establish current liveness. A tool/agent can hang beyond the plan deadline; the next bridge tick expires future authority, while execution may continue.

| Symptom | Action |
| --- | --- |
| `plan id already used` | The ID was used before. Inspect the existing plan/receipt; do not overwrite or retry the same ID |
| `EEXIST` on startup, or `start` reports a lock | Another supervisor or stale crash lock exists. Verify owner process/session offline, then follow recovery below |
| `not a complete bridge setup folder` | The folder was not created by `setup`, was interrupted, or was changed. Files are left untouched; run `setup` with a new folder |
| `unsupported or unverified OMP host` / `OMP executable not found on PATH` | The bridge stops when it cannot identify the OMP executable or verify required runtime/completion evidence. This fail-closed safety check protects against uncertain execution; compatibility problems are bugs to fix. Select a real `omp.exe` through OMP's own installer in an absolute `PATH` entry (relative entries and shims are ignored). If OMP is not on `PATH`, prepend its folder for the current PowerShell window only; the bridge changes no PATH or settings. Preserve state when verification fails. Missing or malformed completion evidence ends the plan `malformed` or `failed` and must not be resent.
| failed (`message_not_confirmed_in_transcript`) | Inspect OMP locally; never resend because a receipt is missing. Manual input, partial or malformed rows, changed identity/prefix, ambiguous compaction or unsupported events may invalidate proof; transcript growth or row length alone does not. |
| queue doesn't advance | Check OMP is running, idle and has no pending messages; inspect failed or malformed receipts (queued plans wait about 5 seconds behind them), expiry and cancellation |
| file/path rejected | Replace symlink/junction/shared roots with a new plain private local directory; never weaken checks |
| `EPERM` when `npm test` spawns | On the tested Node 26 runtime try `node --test --test-isolation=none`; Node 22.23.3 lacks that option. CLI/probe tests still require an authorized child-process-capable environment |
| queue capacity reached | The project holds 128 unfinished tasks. Finished tasks free room by themselves (the oldest finished task's plan is retired; its receipt stays). Wait for queued tasks to finish, or cancel some with `pots cancel` (OMP must be running to close them), then queue again. Never reuse old IDs |
| provider unavailable or quota exhausted | Use OMP's supported provider workflow. This bridge cannot restore unavailable model service or bypass quotas |
| persistence failure | Stop, inspect private state/storage. Do not delete the receipt/lock or resend to manufacture success |

## Runtime wake and coordinator handoff

The extension serializes lifecycle-triggered wake-ups, command tickets and queue discovery on one controller lane; a two-second timer is the bounded fallback for queue changes without a native event. Automatic session startup schedules its first wake asynchronously, without holding the OMP lifecycle callback open.

A coordinator helper is considered only after an exact-session completed receipt has verified each step's user admission and run-end evidence, and current diagnostics confirm the same session/file, idle with no pending messages, the lock held, and no active run. The helper embeds the hash-pinned coordinator script chain and uses the absolute Windows SystemRoot PowerShell executable. Its exit code is not native admission proof; inspect the coordinator's task-specific queue/receipt before treating work as submitted. Failed or malformed plans are never replayed.

While terminal transcript observation is pending, the supervisor polls the persistent plan-abort record every 250 ms and aborts the observation signal when found. This stops future plan steps but does not claim native execution was cancelled; an incomplete admission never advances the receipt's step.

The <=15-second completion-to-next-plan target is bounded by design (a 2 s supervisor/lane-sampling timer, a `control/lane-events.jsonl` completion/idle/blocked feed, and no review gate: a plan that did not complete holds the queue for only about 5 seconds) but has not been measured on a live host; no live qualification is claimed.

## Plans that did not complete, and recovery

Every plan ends in a definite state with a plain reason: `completed` (every step ran to its end), `failed`, `malformed`, `aborted` or `expired`. Receipts written by older versions read as the new words (`unknown` as `failed`, `exhausted` as `completed`, an outcome value `unknown` as `not_seen`) (reason `uncorrelated_end` reads as `end_not_matched_to_message`); no file needs editing. Review project effects in the existing OMP session before authorizing more work. A plan that did not complete is never replayed; it holds queued plans for about 5 seconds and then releases them, so no review step exists. When the supervisor is closed due to an error, fix the storage issue and perform offline recovery first. After a crash, the lock remains. Confirm that **all** writers of the exact saved session are stopped and inspect any in-flight effects, then remove only the exact lock file inside the selected private root. This deliberate manual action is not automatically authorized by a timeout/PID lookup; PIDs can be reused. Uninstall only asks whether a leftover lock still blocks removal: a lock whose program is gone (or that is older than the last PC start) does not block it; any other lock stops uninstall, which names the file and says to delete only that file once no OMP or bridge program runs. The next `open` reconciles nonterminal receipts to `failed` (reason `restart`) before another request. Review them and use new IDs for newly authorized work. No recovery operation restarts owner tasks automatically.

## Upgrade and rollback

Keep a private copy of the old checkout/commit and state before upgrading. Quiesce the chosen session with no bridge request in flight, inspect receipts, and review a diff and offline test results. Load the new source only at a separately authorized same-session resume. Protocol v1 does not silently migrate schemas or assume future compatibility. Never update source files beneath a running extension. Rollback uses the previous reviewed commit and unchanged private receipts; uncertain requests stay failed or malformed and are never replayed. Do not mix versions concurrently against one state root. The optional updater ([updates](update.md)) is different: it only adds a new immutable version folder and moves one pointer in a separate managed install. It never writes a source checkout, takes an install lock so two updates cannot run at once, keeps a backup and the previous version for an explicit rollback, and is not blocked by an open OMP session or a running plan (running sessions keep the files they loaded; the next start uses the new version). For a Windows install, running `pots upgrade` upgrades it in place in one step (the new version is added and verified beside the old one first, and every switched step is undone if one fails; if the version pointer itself cannot be put back, the lock is kept and the message names the one step that fixes it); see [updates](update.md#upgrading-with-setup).

## Uninstall

For an automatically managed Windows installation, use **Settings > Apps > Installed apps > Pi on the Side!** after the selected OMP session is safely closed. The uninstaller checks its private ownership record, exact installed-file hashes, locks, running processes and recorded host registration; unknown or changed files and foreign entries stop removal without deleting them. It recognises every version folder by that folder's own manifest (a runtime-shaped file that no manifest lists is never claimed) and the installer's `backups` folder as owned data. The default **Yes** moves only the verified managed installation and its bridge-owned private state to a same-volume recovery folder. **No** opens a separate permanent-purge confirmation (a purge deletes everything except your handoff file, which it first copies next to the install folder and names in the result); **Cancel** changes nothing. Restore from that recovery folder only after verifying the installation identity and resolving any active work. OMP, Node, projects, original OMP sessions, provider settings and untracked client adapters are not removed. What Setup registered in assistant apps (the Claude Code server entry and skill, the ChatGPT / Codex `config.toml` block) is removed only while it is still exactly what Setup wrote; a host entry is removed only when its recorded ownership digest still matches. The uninstaller also removes what older versions left behind, with the same proofs as Setup (see [updates](update.md#older-copies-are-left-alone)): older setup folders, dated builds, stale entries in Installed apps and Startup. Anything still in use, or that it cannot prove is Setup's own, stays and is listed. This does not undo project edits, provider submissions or tasks already running.

If the install folder is already gone but Windows still lists Pi on the Side, `pots uninstall` removes that one entry together with this install, and so does Settings > Apps from an install that still works; the folder is compared without regard to letter case. It does so only when the entry names that folder and the uninstall command Setup wrote for it: an entry for any other folder or command is never touched, and one such leftover entry does not stop the removal of an install that still works. If such a folder has come back by the time its entry would be removed, it is a working install again: it is left alone and the result says so. Plain `pots uninstall` takes no other install that still exists.

`pots uninstall --all` removes nothing by itself. It prints every install that Windows lists (the folder, and that its files would be moved to a private recovery folder next to it, not deleted), and says to add `--confirm-offline` to go ahead. `pots uninstall --all --confirm-offline` removes them all. "All" means this install plus every install Windows lists: when Windows lists none, it removes this install only, and when Windows cannot give the list, it stops and removes nothing.

If one install is removed and a later one cannot be, the result says which installs were removed and where each one's files went, and which one was not. The `pots` command goes with the install that owns it, so then the way to uninstall again is Settings > Apps > Installed apps, and the result says so.

The purge window says exactly where the handoff file goes: next to the install folder, readable by anyone who can open that folder. Files outside the install folder that you changed after Setup wrote them (a changed Startup launcher, a changed assistant entry) stay where they are. If the confirmation window fails or is not answered within five minutes, wake-ups are switched back on.

A file in `coordinator-resume` that Setup did not record as its own (one you made, or one you changed after Setup wrote it) is treated like any other unknown file: removal stops, `pots uninstall --details` names it, and it is never moved into the recovery folder and never purged. Move it out of the install folder, then uninstall again.

The wake-up scheduled task, if the install made one, is deleted by the uninstaller after it has paused the watchdog, and only when the task still carries this install's marker in its description; a task without the marker is never deleted. What Setup registered in Claude Desktop (its own entry in `claude_desktop_config.json`) is removed the same way, only while it is still ours. `pots doctor` shows the state of the task and the watchdog before you decide to uninstall.

## In-process enable, disable and status

With the reviewed extension loaded and a saved OMP_BRIDGE_CONFIG binding, use /bridge enable, /bridge disable and /bridge status. Normal bound startup enables quietly; no separate worker or supervisor terminal is started. Disable is process-local, leaves queued plans intact, marks active plans failed and never interrupts native OMP work. Enable checks identity again and refuses competing/stale locks or a busy native session. Never use enable as recovery for a plan that did not complete. Status reports local readiness and ownership, not remote desktop/provider connectivity. A subsequent bound OMP launch enables again; this release has no persistent disabled preference.

## Queued work while the terminal appears idle

Use native `/bridge status` and the private `control/dispatch-diagnostic.json` snapshot to distinguish advancing polls from stale observations, actual busy/pending gates, a closed supervisor, and failed or malformed receipts. Compare snapshot PID/session match with the intended live writer. A last answer on screen alone does not establish runtime idle. Preserve plans and receipts while investigating; an expired receipt alone is not a queue block. Saved completion, dispatch acceptance and verified project success remain separate evidence. Do not infer the cause of an old stall from a later restart that recovered it.

## Sharing a private sanitized trace

Open the setup folder, then its `control` folder. Share only `bridge-trace.jsonl` and, if useful, `bridge-trace.jsonl.1` and `.2`; review those files before sharing. Do not share the whole state folder, credentials or transcript. Trace files contain fixed structured event names, time/process metadata, boolean gates, bounded step counts, receipt states and sanitized error/reason categories; never task text, session/plan identifiers, capabilities or paths. Three files of at most 48 KiB each cap retained trace data at 144 KiB. Heartbeat and review-block events occur at most once per minute; unchanged gate reasons are suppressed. At most 32 records wait in memory; overload is dropped and counted. Files use the existing private directory protections and mode 0600. Logging failure never changes dispatch or receipts. Logs describe observations and do not establish the original stall cause or project success. Existing running extensions acquire this logging only at a coordinated safe load of the tested release.
Rotation uses an exclusive empty trace-write.lock inside control, so concurrent processes cannot exceed the trace cap. A leftover trace guard stops logging only and is never reclaimed by logging; inspect it offline after all related writers have exited. Uninstall and Setup treat a guard file as left over only when its owner process is gone, it predates the last PC start, or it names no owner and is over 30 minutes old; supervisor locks keep their own rule. Preexisting malformed/unsanitized traces are preserved and refused, not repaired; inspect files before sharing.

## Coordinator event feed

`control/lane-events.jsonl` (schema in [protocol](protocol.md#lane-events-coordinator-visible-transitions)) is the machine-readable completion signal: tail it for `plan_done` (this plan ended; its `state` says how: `completed`, `failed`, `malformed`, `aborted` or `expired`) and `idle` (the lane can take the next plan). Inspect a `failed` or `malformed` plan's receipt and the saved OMP session, then decide; the bridge never replays it. A bridge that is not running writes nothing: absence of new rows is not idle evidence.

## Lane watcher

Each lane started through the launcher logs `IDLE`, `BUSY`, `RESULT` and `GONE` lines in `control/lane-watch.log` ([format and settings](lane-watch.md)). To see what is new, run `node bin/bridge.mjs watch-lines "<connections-or-state-folder>" --peek`; to see each lane's latest state, run `watch-state`. No line at all means the lane was not started through the launcher, the watcher is off in `control/lane-watch.json`, or nothing has changed. `ERROR` lines mean the watcher could not read the lane feed or scan the result folder; the launcher and OMP keep running. A `GONE reason=lost` line means the launcher window was closed without a clean exit. Delete nothing in `control` to "reset" the watcher: sequence numbers continue across restarts, and the coordinator cursor repairs itself if the log is deleted.

## Starting a lane on a verified model

Use one of these to start a task on a chosen model. Give the model name exactly as OMP lists it (`omp models`); Pi on the Side keeps no list of its own.

- `node bin/bridge.mjs lane-task "<state-folder>" <model> "<task>"`
- `node bin/bridge.mjs queue "<state-folder>" "<task>" --model <model>` (the same check, printed as JSON)
- the MCP tool `bridge_enqueue` with its optional `model` field

Each one asks OMP to switch with `/model`, then waits for OMP itself to say which model is running. If OMP says something else, the switch is tried again (up to six times). The task is queued only after OMP reports the requested model. If that never happens, nothing is queued, the command exits non-zero with `model switch not verified; task not sent`, and a `start_failed` line is added to `control/lane-events.jsonl`. If the model is fine but the task cannot be confirmed stored, the command exits non-zero with `prompt delivery not confirmed; lane start failed` (the plan is not there) or, when the plan list could not be read at all, with `prompt delivery not confirmed; the task may have been queued, so check pots status before queueing it again`, and a `start_failed` line. A queue write that fails at the disk (for example disk full) also leaves a `start_failed` line; the queue's own refusals (full, text not accepted) print their reason and leave none. A name OMP does not know, or one that several providers carry, is refused straight away and is not retried. A retry of the same plan ID in `bridge_enqueue` returns the existing plan and does not switch again.

While the newest `/model` request is not proven, the lane holds back every task. `queue` and `bridge_enqueue` refuse new tasks (`model switch not verified; task not sent`), and the lane will not start a task that was queued earlier. This includes a plain `command <state-folder> <id> /model <model>` that OMP did not prove, and a `/model` request that has been sent but not yet answered (so a task can never slip in ahead of a switch on its way). A task that is already running is not stopped. A receipt file that cannot be read counts as unproven, so a damaged file cannot open the gate, and the bridge skips it instead of stopping, so a later verified switch still runs.

To get a held lane moving again, run a switch that OMP proves: `node bin/bridge.mjs model "<state-folder>" <model>`. Asking for the model the lane already runs is proven at once, so `bridge_lanes_status` (field `model.actual`) tells you a name that always works. Until then, `bridge_lanes_status` shows `model.holdingPlans` and a lane with waiting tasks needs attention. Cancelling the waiting tasks also stops the wait. A `/model` request that nothing answers (for example after a power cut) stops holding by itself after 5 minutes and is never sent; `command-cancel <state-folder> <command-id>` ends it at once, also when it never got its first receipt, and a leftover `control/command-<id>.lock` older than a minute is removed the next time that record is updated.

`bridge_lanes_status` reports `model` as `actual` (what OMP says is running), `requested`, `state` and `holdingPlans`. A switch OMP could not prove (`state: "mismatch"`) and a failed start both set `needsAttention`.

Only the model switch is verified this way. Other post-start commands (title, mode) are not covered: their receipts stay `returned-unverified` and must not be treated as done.

## Continuing a stopped lane, and spending limits

After a restart or crash, `pots status` and `bridge_lanes_status` say a lane is "stopped" when a task was running and no bridge is running it any more (OMP closed or crashed, or its bridge stopped), and the coordinator wake-up treats it as needing attention. `pots lane restore <name>` (the name is the one `pots lane list` shows) continues it in this window with OMP's `--restore`, the same bridge and the same lane files, so the lane's receipts and queue carry on. It refuses, and changes nothing, when OMP says a running OMP still owns the lane (its window may still be open with its bridge stopped: run `/bridge status` there, fix what it says, then `/bridge enable`; or close that window), when OMP cannot say, or when the saved session is gone (then start a new lane). It removes only the lane's own lock left by the stopped run, and only when that run is gone. The task that was running is marked failed (`restart`) and is never sent again, because OMP itself carries on with its unfinished turn; tasks still waiting in the queue go on as normal.

To limit what a lane may spend, add any of `--warn-cost <dollars>`, `--max-cost <dollars>` and `--max-time <time such as 30m or 2h>` to `start` or to `pots lane restore`. They are passed to OMP as they are; with none given, there is no limit.

This is the one exception to "never steals" and "not automatically authorized" above: `start` itself still refuses any leftover lock. `pots lane restore` removes a leftover lock only when OMP's own `session lease` says no running OMP owns the session (an answer of "unknown" refuses), and the lock names this lane's session and is provably stale (its program is gone or the PC restarted since).

## When the lane list is full

The list holds up to 64 lanes. When one more lane is connected by name (`setup-auto --session`, `connect`, or `pots lane restore` for a lane that is not on the list), Pi on the Side first takes finished lanes off the list by itself, oldest first, until 48 are left, and then adds the new one. A lane counts as finished only when OMP is not running for it and nothing in its files has changed for 2 hours. A lane that is running, or that cannot be checked, is never taken off. Only the entry in the list is removed: the saved session, the lane's folder and its results stay where they are. Before every removal the old list is kept as `connections.json.bak1` (the last five are kept as `.bak1` to `.bak5`), and the new list is read back after it is written; if that fails, the old list is put back and the message says so. `pots install` and the assistant adapter still only fill free places and never take a lane off the list.

If every lane is running or stopped less than 2 hours ago, nothing is removed, and the message says how many are running and which command frees a place:

- `pots lane close <name>` takes one lane that is not running off the list, without the 2 hour wait. It refuses a running lane and the last lane on the list (the list cannot be empty). The name is the one `pots lane list` shows.
- `pots lane close --finished` takes every finished lane off the list at once (one lane always stays).
- `pots lane list` shows each lane on the list as running or finished, and the lanes that were taken off and can be brought back.
- `pots lane restore <name>` puts a lane that is not on the list back (using the launcher Setup saved for it) and then continues it as described above. If the list is full, finished lanes make room the same way.

A lane that was taken off the list and had stopped in the middle of a task is not shown as stopped any more; `pots lane restore <name>` brings it back and continues it.

## Registry errors when lanes start together

The connections registry is written to a temporary file, flushed, and renamed over the old one, so a reader never sees half a file from this code. A writer also holds `connections.lock` while it works. A valid registry is read at once even while a lock or temporary file is present. If the registry is missing, half-written or briefly unreadable, readers retry for about two seconds before giving up (`connections registration busy` if a lock or temporary file is present, otherwise `invalid connections registry`). A second lane registering at the same time waits up to five seconds for its turn. A lock left behind by a crash is removed automatically the next time a writer needs it, but only when the program that made it is gone or the PC has restarted since; a lock whose program still runs is never taken. If a lock stays and no bridge command is running, delete `connections.lock` yourself. A connection whose saved OMP session was deleted or changed is reported as unavailable by the status tools and `pots status`, and it never blocks the other connections or a new one; `pots install` removes only that registry row, never any saved session or project file.

If `setup` fails part-way, it removes the folder it just created (only its own empty entries). A folder that already existed, including one left by an earlier interrupted setup, is never adopted or removed: inspect it and delete it yourself, then run `setup` again.
