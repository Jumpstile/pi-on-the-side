# Tester checklist

Use the [v1.0.8 quickstart](release-quickstart.md). Pi on the Side is designed to work across OMP versions; compatibility problems are bugs to fix. Not every past or future release has been tested. Verify each release asset against the digest GitHub shows for it and record the exact source tag. No local patch or manual JSON configuration is needed.

1. Record Windows, Node, OMP and Claude Desktop versions. Use your own disposable saved session and provider account on the same computer.
2. Run the one-line install from the quickstart (or `pots install`). Check that it downloads nothing but the release it checks. Expect one plain sentence that says what was done and the next step; every saved session you have is connected, and nothing has started OMP or proven a live connection. Run `pots install` again and check the per-user Apps entry, key, connection data and receipts remain intact. To test an upgrade, run `pots upgrade` over an older install while one OMP session is open: it must say "Upgraded to X. A session is open, so the new version starts with the next session." and must not ask you to close anything.
3. Close any other instance of one connected session, then open that project with its `Start-OMP.ps1` (listed by `pots install --details`) and type START. Verify `/bridge status`, disable and enable. Repeated enable must not create another supervisor. No global extension installation is expected.
4. Open the verified `.mcpb` with Claude Desktop and confirm its own install prompt; type the assistant folder that `pots install --details` lists. Leave the write-access file empty when Claude Code or the ChatGPT app is the directing assistant, otherwise use the **Permission file** path from `pots install --details`; read the exact named connection first. Record the seven tool names and host approval behavior. Current controller-build Claude chat integration is the behavior under test.
5. Only if you approve quota use, enqueue one harmless single-step prompt with a fresh UUID and read that exact receipt. An identical retry keeps the ID. The receipt ends as `completed` (the task ended; `taskSuccess` still says `unverified`, so `completed` never proves the project is right), `failed`, `malformed`, `aborted` (future steps cancelled, as in the cancel step) or `expired` (the deadline passed); a `failed` or `malformed` task must not be retried as fresh work.
6. Optional disposable tests: cancellation affects future steps; native abort/restart preserves uncertain outcomes without replay. Use [offline recovery](operations.md), not unexplained lock deletion. A different directing client needs its own credential and explicit handoff; no automatic takeover is supported.

Report only versions, steps, pass/fail, receipt states/reason codes and minimal synthetic reproductions. Exclude private paths, names, keys, IDs, prompts, transcripts, logs and personal screenshots. Do not use maintainer sessions, change global OMP settings, open listeners or attempt quota workarounds.
