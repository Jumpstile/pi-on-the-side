# Architecture and protocol v1

Advanced reference for how the local queue, OMP session, saved records and optional assistant connection fit together. Most users can start with the [quickstart](release-quickstart.md).

```text
authorized local terminal / local assistant
                 |
           bridge CLI
                 |
       private local filesystem
        plans + control + receipts
                 |
   supervisor inside an OMP main session
      exact config ID + cwd; session lock
                 |
     OMP sendUserMessage + lifecycle events
                 |
        configured OMP model provider
```

The CLI and state store contain no provider/network code. The OMP extension supplies the runtime adapter. Assistants with approved local execution can read the same queue; writes also require explicit controller ownership. Remote assistants cannot access it merely because an API or MCP is available in their product. The optional stdio MCP adapter (`bin/mcp.mjs`, [desktop adapter](desktop.md)) uses explicitly pinned setups. [Controller ownership](controllers.md) adds a local capability digest and exclusive write gate; plan and receipt schemas stay unchanged.

## Filesystem wire format

All records are UTF-8 JSON with a trailing newline. Each state root contains `plans`, `receipts`, `control` and one `supervisor-<sessionId>.lock`. IDs are lowercase UUIDs; paths are generated from validated IDs. Config keys are `cwd,root,sessionId`, with `coordinatorWakeups` and `clients` added in folders made by `setup`. A root is provisioned explicitly and existing directories are never adopted by `init` or `setup`. A `setup` folder also holds its `config.json` and `launch.json` ([layout](advanced.md)).

Plans: `plans/<id>.json`, schema `{version:1,id,sessionId,expiresAt,steps}`. Each step has exactly `{prompt,continueAfterEnd}`. `expiresAt` is Unix milliseconds; new plans must expire in (now, now+24h]. Plans are immutable, published with exclusive hard-link creation. The retained plan reserves the ID even before a receipt exists. Queue selection is lexicographic UUID order, **not FIFO**; use one plan for ordered dependent prompts. A state root keeps at most 128 plan files. When it is full, queueing retires the oldest plans whose receipt is terminal (`completed`, `failed`, `aborted`, `expired`, `malformed`): only the plan file is removed, the receipt stays, and the ID is never accepted again. A plan without a terminal receipt is never removed, so 128 unfinished plans refuse new work (`queue capacity reached`) until some finish or, once OMP reaches them, are cancelled. Do not delete records to reuse IDs.

Lists and retired plans: `pots status`, `bridge_status` and `bridge_lanes_status` walk the plan files only, never `receipts/` (it grows without limit), so they stay bounded. A retired task therefore drops out of those lists, and the `pots status` "a queued task was not started" line for an `expired_before_submission` task disappears with its plan (the watcher's `EXPIRED` line is the one notice). `bridge_receipt` answers from the receipt alone when the plan is gone and says `unknown plan id` only when neither file exists; `bridge_cancel` on such a task says it already ended.

Receipts: `receipts/<id>.json`, owner-local facts including `version,id,sessionId,state,nextStep,updatedAt,outcomes,taskSuccess,automaticReplay` and a bounded reason. Outcomes have step index, API-return observation, exact user-record admission where verified, and run-end observation. No prompt, assistant output, tool arguments or tool results are persisted in receipts. Prompts do persist in the private plan file; they must not contain secrets. A receipt may report:

| State | Meaning |
| --- | --- |
| no receipt / CLI queued | Plan has not been reserved |
| reserved | Durable identity reservation, no API attempt yet |
| submitting | Durable intent before API call; outcome not yet observed |
| submitted | OMP has been given the message (the call may still be open while the task runs); delivery and success are unproven until the saved-session check at the end |
| waiting | Previous step's correlated terminal event and admission observed, next transition authorized |
| completed | All finite steps ended; task success remains unverified. Receipts that older versions wrote as `exhausted` read as `completed` |
| failed | The plan did not complete. A specific reason says what happened (`start_event_missing`, `end_not_matched_to_message`, `message_not_confirmed_in_transcript`, `cancel_check_failed`, `overlapping_or_unexpected_run`, `supervisor_shutdown`, `restart`, `invalid_plan`, `plan_identity_mismatch`, `admission_fence_unavailable`, `session_changed_before_submission`, `context_changed_before_submission`, `submission_exception`). Kept as a receipt, never replayed, holds queued plans about 5 seconds and then releases them. Receipts that older versions wrote as `unknown` read as `failed` |
| malformed | The end was matched to the submitted message but its terminal field was unreadable (reason `malformed_end`). Kept as a receipt, never replayed; it holds queued plans about 5 seconds and then releases them |
| aborted | Future steps cancelled; active execution may continue |
| expired | Deadline reached; active execution may continue |

`taskSuccess` is always `unverified`; `automaticReplay` is always false. API return, transcript admission, terminal observation and successful work are separate facts. A failed plan may conservatively occur before any API attempt.

Control: `control/<id>.json`, `{version:1,id,sessionId,action:'abort'}`. Cancellation is persistent and checked before submission and on each tick/end event. It does not call a remote or native abort API. There is no review step: a plan that did not complete is never replayed and never blocks the queue for more than about 5 seconds. New work needs a fresh plan ID and explicit scope.

Terminal admission keeps the existing persistent-cancellation monitor active through final native semantic revalidation and its awaited proof write (250 ms observation interval, each cancellation read bounded to one second). For `native-lineage-v1`, the final proof-persistence callback performs another bounded cancellation read **after** that write. Observed cancellation prevents advancement and records `aborted`; an unavailable cancellation read fails closed as `failed` (reason `cancel_check_failed`). Native reconciliation then retains its post-write file-identity and live-semantic checks, followed by the supervisor's synchronous owner/token and semantic-proof commit gates. No additional complete transcript scan follows this final cancellation observation.

The successful final bounded read is the receipt's cancellation-observation boundary, not an atomic transaction with an unrelated process publishing an abort file. An abort first published after that observation may lose to receipt advancement, even while the remaining identity checks complete; the still-active monitor can observe it but is not an atomicity guarantee. Such late cancellation does not authorize another send: every future submission retains its separate persistent-cancellation checks. Cancellation never interrupts native execution, replays a step, or proves task success.

## Core JavaScript API

`Store(settings, now?)` validates configuration. `ready()` validates paths. `enqueue(plan)` validates target/schema/deadline and reserves the plan ID. `ids()` returns bounded sorted IDs. `receipt(id)` reads one private receipt. `abort(id)` publishes cancellation. `Supervisor(store, adapter)` exposes `open`, `tick`, `continue`, `started(token)`, `ended(token, willContinue)` and `close`. Call `open` before scheduling anything, and `close` during orderly shutdown. The OMP adapter serializes lifecycle and polling calls through the core lane; failed persistence closes it before any subsequent API send.

The runtime adapter must implement `isIdle():boolean`, `send(text):Promise<void>|void`, `fence(text):Promise<object>` and `admitted(fence, {signal,onProgress,onVerified}):Promise<boolean>`. It supplies unique physical-run tokens via `started`/`ended`. Admission independently identifies the exact sole user message submitted after the fence, then durably records path-free fence identity and append-integrity evidence before marking admission. A terminal event must be correlated to the same physical run; missing or ambiguous correlation ends the plan `failed` (never completed, never replayed). Neither API success nor assistant text is valid delivery evidence. See [adapters](adapters.md).

Fence acquisition and API submission retain their existing 2.5-second and five-second bounds. Transcript admission has no aggregate byte, record-count or elapsed-time ceiling: it processes fixed 256 KiB probes, buffers only small records up to 64 KiB, and parses larger JSONL records incrementally while retaining compact correlation fields and structural state. It rechecks the session/file identity and immutable pre-send prefix, requires complete newline-terminated valid records and exactly one exact user message, streams a cumulative SHA-256, then rereads the append range in bounded chunks and verifies the same identity, prefix and final size before persisting the proof. A filesystem watch wakes reconciliation with a 250 ms fallback; supervisor shutdown aborts observation. Partial, malformed, branch, compaction, changed or nonmatching evidence ends the plan `failed` with a specific reason; uncertain work is never replayed. Progress checkpoints and final path-free hashes are internal receipt metadata and are not relayed by MCP. A terminal observation still does not establish task success.

## Optional stdio MCP API

`bin/mcp.mjs` serves MCP 2025-06-18 as newline-delimited JSON-RPC 2.0 on stdin/stdout for the setup or named connections folder in `OMP_BRIDGE_STATE` ([desktop adapter](desktop.md)). `bridge_enqueue` calls `Store.enqueue` with a one-step, 24-hour (the wait counts), `continueAfterEnd:false` plan; `bridge_cancel` calls `Store.abort`. Both writes require the locally configured `OMP_BRIDGE_CONTROLLER` capability to own the target session, and run within its exclusive controller write gate. `bridge_status` and `bridge_receipt` remain shared reads. Acquisition and handoff are local CLI actions, not tools. No display-name identity or tool-supplied key is accepted.

- Lifecycle: `initialize` (params: string `protocolVersion`, object `capabilities`, `clientInfo` with string `name` and `version`) is accepted once per process; tools are served only after `notifications/initialized`; `ping` works at any time; notifications never act.
- Identity: every call revalidates the setup folder and saved session header; the first valid call pins session ID, project folder, saved session file and executable for the process lifetime, and any later change is refused.
- Relayed data: receipts only in their exact shape with a reason from the core's fixed reason-code list; plans without receipts only when they pass `plan()` rules (expiry checked for type only) for this session under their own ID. Otherwise `receipt not recognized` or `plan not recognized`. A duplicate enqueue is reported only for an identical, recognized single-prompt plan.
- Bounds: frames up to 64 KiB; at most 16 pending operations, each pending until its reply is handed to stdout; input read only while stdout is not backed up; more than 1 MiB of unconsumed input from one read stops input without acting. Errors are fixed text; stderr diagnostics are fixed and written at most once each.

## Optional update API

`src/update.mjs` ([updates](update.md)) adds no record to a state root and never writes one. A confirmed apply or rollback holds only `<install>/activate.lock` (the install lock, so two updates cannot run at once), then replaces the pointer atomically; it does not look at supervisor locks, queued plans or open sessions. A managed install holds `bridge.mjs` (fixed launcher), `current.json` (`{"version":1,"current":<semver>,"previous":<semver>|null}`, replaced atomically), `staging/` and `versions/<semver>/`. `pots install` keeps one managed install, `<install folder>\runtime\current`, for every connected session, and puts copies of files the installer itself replaced in `<install folder>\backups\<timestamp>\`. Each version folder holds exactly the files its own `release.json` lists (`{"version":1,"release","digest":"sha256:...","files":{path:sha256}}`) plus `release.json`; a release declares that list in its `package.json` `runtimeFiles`, so changing the list never blocks an update, upgrade, rollback or uninstall. `RELEASE_FILES` is only the running version's own list, used as the expected list for a bundle that declares none. The CLI exposes `update check|install|apply|rollback|migrate`. The launcher passes `{ managed: <install> }` to `main`; ordinary apply/rollback take it only from the launcher. The explicit `update migrate <existing-install-folder> <state-folder>` command uses the new package with an existing verified install, retaining the same lock and verification rules and starting no OMP. `checkUpdate`, `installUpdate`, `applyUpdate` and `rollbackUpdate` return `{ status, current, ... }` with the fixed statuses listed in the update docs. `runGh(args, { timeout, maxBytes })` is the bounded `gh` child runner.

## Durability and recovery

A single session lock is acquired with exclusive `wx` and held open for the supervisor lifetime. A second supervisor fails rather than stealing it. Restart after graceful close reconciles every nonterminal receipt to `failed` (reason `restart`). Crash leaves the lock; offline owner inspection is required before removing it. In-flight or waiting steps are never replayed, including reserved/submitting crash windows. Prompts without receipts can be picked up after offline lock recovery because no side effect precedes the durable reservation.

JSON writes fsync a new same-directory temp file before atomic rename. On Windows, replacing a receipt that another reader (for example a concurrent status read) holds open fails with `EPERM`/`EACCES`/`EBUSY` until that handle closes; the same rename is retried for up to two seconds. If sharing failure persists past two seconds the write fails closed: the lane stops and nothing is replayed automatically; owner review is required. Failure before the API call prevents that submission. Failure while persisting an API return or later observation can leave an already-submitted task running with an uncertain outcome. The rename succeeds at most once and never exposes a partial record. A reader racing a replacement can observe the swapped file identity and reports `file changed` rather than mixed content. Exclusive plan/control publication uses hard links to avoid replacing prior IDs. Partial `.tmp` files are ignored and do not count toward queue capacity; cleanup is an offline owner action. Atomic replacement does not guarantee persistence through controller/storage power loss. This protocol requires a private local filesystem, trusted code and no second writer bypassing the lock.

## OMP transcript evidence

The adapter capability-checks `sessionManager.getSessionFile`. It verifies the v3 session header identity, plain path and file identity, then fences the file size and a bounded suffix hash before calling `sendUserMessage`. Terminal reconciliation rechecks the immutable fence and file identity, streams complete appended records in bounded chunks and verifies cumulative append integrity in a second bounded-memory pass. There is no aggregate transcript-growth or record-size rejection: large JSONL rows are parsed incrementally and valid growth beyond 2 MiB remains eligible for exact correlation. Small rows are parsed directly; large rows retain only correlation fields and JSON structure, not their full text. Exactly one appended user record must match the submitted text hash; assistant/tool echoes do not count. A single OMP compaction record may appear anywhere after the sole user record, including mid-run, only when the last message record is a `stopReason: "stop"` assistant record after that user; only `custom` or the compaction record may follow that final stop, plus at most two OMP `custom_message` records (extension context entries with a string `customType` of at most 128 UTF-8 bytes, boolean `display`, and string or array `content`, and no `message` or `role` field). `custom_message` never counts as a user or assistant record. Multiple compactions, compaction before the sole user, branch-summary records, multiple user inputs, partial tails and unavailable evidence end the plan failed.

Device/inode identity is read with bigint stats and stored in receipts as canonical decimal strings, avoiding Windows `Number` precision loss. File offsets remain safe integers for Node's read API. Streamed JSON parsing retains at most 256 structural frames; this is a nesting/schema guard, not a record-byte limit.

OMP clones lifecycle notifications and supplies history snapshots at agent end. The adapter correlates the latest assistant `message_end` within the current physical-run epoch with the final assistant snapshot at `agent_end`, using a SHA-256 key of timestamp, provider, model, stop reason and content. The serialized input is limited to 64 KiB. Usage and completion bookkeeping are excluded. The observation resets on start and is consumed once on end. Up to 100000 distinct snapshot keys are retained for this adapter lifetime without eviction; a key seen in a prior epoch makes the current run ambiguous even if fresh evidence follows. Capacity exhaustion disables terminal correlation until an offline-reviewed restart. Missing, malformed, oversized, reused or mismatched snapshots end the plan `failed`. This in-memory history is not cross-process replay protection: restart recovery still marks unfinished receipts `failed` and never replays them. No assistant content is persisted in receipts. This association does not replace exact transcript admission or prove project success.

The session header is read from the first 32 KiB. Only complete newline-terminated leading records are parsed. The first record must be the `type: "session"` header, or a correctly shaped OMP title slot immediately before that header. A title slot is accepted only in its verified shape (`SessionTitleSlotEntry` / `serializeTitleSlot`): a JSON object of exactly 256 UTF-8 bytes including the newline with `type: "title"`, `v: 1`, string `title`, `updatedAt` and `pad`, optional `source` of `"auto"` or `"user"`, and no other keys. Any other leading record (`null`, numbers, arrays, `{}`, messages, compaction, `title_change`, malformed title slots) fails closed. Records after the header are never parsed for identity, so header-only files and long second records are accepted. An incomplete, oversized, malformed or identity-mismatched header fails closed.

The pre-send fence hashes the bytes from `start = max(0, size − 32 KiB)` to the fenced size. OMP rewrites its fixed-width title slot in place (automatic title after the first prompt, or a user rename) without changing the file length or any other byte, so for a session of at most 32768 + 255 bytes (fence start 0–255) some or all of that slot is inside the fenced range. When the window overlaps bytes 0–255 and the file head is a verified title slot (above), the fence hashes only the window bytes from offset 256 on, and verification accepts that hash only while bytes 0–255, read from the file head independently of the window, are still a verified title slot. A window starting at 256 or later never involves the slot. A whole-window hash recorded before this rule is still accepted while the slot is unchanged. Every other fenced byte, the header, the slot's own shape, the file identity and size, and the appended-region rules remain exact: a rewrite of any other fenced byte, or a non-slot/malformed record at byte 0, still reports `fence_changed` and ends the receipt `failed`. Receipt `admissionFence` fields are unchanged. Before this rule a one-step plan on such a session ran to a normal finish but was recorded as an unresolved outcome (now `failed` / `message_not_confirmed_in_transcript`; trace `admission_failure: fence_changed`).

## Host lifecycle contract

`agent_end.willContinue` is read after a bounded, read-only probe of the running OMP executable (its `--version` answer must have the form `omp/<major>.<minor>.<patch>`) and the required runtime capabilities. There is no list of supported OMP versions: every version follows the rule below. No caller-supplied field or environment variable is trusted as proof.

- `false` is a candidate terminal observation; the bridge advances only after exact saved-session admission and correlated assistant evidence.
- `true` means OMP may continue; it never authorizes another bridge step.
- A missing value means the run finished, the same as `false`. A present but malformed value ends a matched run as `malformed` (reason `malformed_end`); an end that cannot be matched ends `failed` (`start_event_missing` or `end_not_matched_to_message`). Both release the queue after a short settle time and neither is ever replayed.

Dated test observations are recorded in [verification](verification.md). These guards prevent uncertain observations from being treated as success; they cannot prove the requested project work succeeded.

Unowned native work has a separate dispatch hold, not a receipt outcome. A malformed continuation field retains an evidence hold; a later valid END can resolve it only for the same unchanged user/assistant evidence. Terminal release additionally requires a fresh same-phase `message_end` matching the bounded assistant key and native ID (when present), a terminal stop, unchanged start lifecycle epoch, and no staged successor. At a subsequent supervisor wake, the same owner/context/binding must be native-idle with no pending messages, no active bridge plan/run/continuation, and no unresolved terminal conflict/message. Only then is the evidence hold cleared. A new START invalidates a pending release. Replayed identities, changed evidence, conflicting late observations, lifecycle changes or ambiguous START/message ordering keep failing closed until a new session lifecycle. No historical receipt is reviewed, relabeled or replayed by this path.

The supervisor checks the idle/hold gate before reading the queue and again, with no intervening await, immediately before writing the durable `reserved` receipt. A START or hold that lands between the two leaves the plan queued with no receipt, so the next wake can release a validated hold and reserve it normally. A context change after that second check, including one during the reservation write, still ends that plan `failed` (reason `context_changed_before_submission`) before any send.

When `terminalSignal` returns undefined, the existing bounded `run_correlation` trace records `terminalSignalReason`: `non_boolean_field` for a present malformed field. The trace allowlist rejects every other value and records no host string, field value or task/message text. Existing rotation and backlog limits are unchanged.

## Named routing

A connections folder holds one bounded connections.json record with version 1 and an array of {name,root,binding}. Binding records have sessionId,cwd,sessionFile,executable captured from setup; they are private local metadata and are never included in assistant results. Registration is a local operation (the `connect` command, Setup, or an adapter holding the controller credential) with a short exclusive writer lock. Interrupted registration requires offline inspection; readers refuse extra entries. The adapter reads the registry on every call and validates selected identities before every action. No caller-supplied root/path is accepted. In named mode every enqueue/cancel/receipt has a connection string from the declared enum; missing or unknown names fail without a write. Status without connection lists bounded observations for every authorized name.

See [OMP compatibility](host-compatibility.md) for the overview. If host identification or required capabilities cannot be verified, startup stops before acquiring a lock or sending queued work.

## Local dispatch observations (v0.2.6)

The OMP extension writes `control/dispatch-diagnostic.json` as private, best-effort status metadata. Protocol version 1 records bridgeVersion, process PID, observation time, poll count and last poll start/finish, actual idle/pending/session-match flags, supervisor presence/closed/lock state, active receipt state, physical-run presence and a fixed error category. It contains no task text, provider/controller credentials, raw exceptions or advisor names. Null flags mean unavailable observations. Polls normally recur every two seconds; stale observations are not health proof. One independent writer and one latest pending snapshot bound persistence work. Status-write failure neither closes nor bypasses the supervisor. Repeated closed-lane errors preserve the preceding causal fault category.

This record is not a plan, controller grant, completion receipt, admission proof or recovery instruction. Existing CLI/MCP receipt shapes are unchanged. Check status still establishes process/binding/extension/lock identity; consult observations for live dispatch gates. Never clear a pending-message guard, remove a live lock, replay a request because a status record appears idle. A compaction record or a line over 8 MiB can legitimately leave a completed native turn with a `failed` receipt (`message_not_confirmed_in_transcript`); inspect the saved outcome. It is never replayed and holds queued plans only for the settle time.

## Lane events (coordinator-visible transitions)

The extension appends one JSON line per lane transition to `control/lane-events.jsonl`. It is an append-only, best-effort, private observation file for the directing coordinator to poll or tail; it is not a receipt, admission proof, plan, grant or recovery instruction, and a write failure never gates dispatch, admission or receipts. Rotation keeps two files of at most 32 KiB each (`lane-events.jsonl`, `lane-events.jsonl.1`); read the `.1` file first, then the current file, and order by `seq` within one `pid`. Writers take turns through a small guard file (`control/lane-events.lock`); if something held it when its writer was done, that program removes it at the next write to that lane's log or from a short retry of its own (a few seconds). A real writer holds the guard for a few milliseconds, so the next writer takes over a guard that has been there for more than 10 seconds, also when Windows has given its owner's process number to another program. A guard younger than 10 seconds whose owner still runs is never removed by another program; a guard whose owner is gone is taken at any age; a guard that cannot be read is left for 30 minutes (or until the PC restarts). Up to 64 records wait in memory; overload is dropped, and so is a record that could not be written, and both are counted in the `dropped` of the next row that is written (a lost row that carried a count passes it on too). Files use the control directory's private protections and mode 0600; a linked/non-plain directory or file stops logging only.

Row (protocol version 1; only these keys, only these vocabularies, no task text, prompts, free-form errors, host strings or paths):

| Field | Meaning |
| --- | --- |
| `version` | `1` |
| `seq` | Per-process counter starting at 1 (resets when the bridge process restarts; use with `pid`) |
| `time` | Epoch milliseconds when the transition was recorded |
| `pid` | Bridge process ID |
| `sessionId` | The bound OMP session (the lane identity) |
| `event` | `idle`, `busy`, `plan_done`, `model_switched`, `model_mismatch` or `start_failed` |
| `planId` | Present on plan events; on `busy` it is the active bridge plan when one exists; absent on `idle` |
| `state` | `plan_done`: `completed`, `failed`, `aborted`, `expired` or `malformed` |
| `reason` | Fixed vocabulary: the receipt reason for plan events (for example `all_planned_submissions_ended_success_unverified`, `message_not_confirmed_in_transcript`, `restart`, `end_not_matched_to_message`, `malformed_end`); `native_idle`, `native_busy`, `pending_messages`, `plan_active`, `bridge_stopped` for lane edges; `model_unverified` or `prompt_not_delivered` for `start_failed`; anything else is written as `other` |
| `dropped` | Count of records dropped before this one, when nonzero |
| `requested`, `model` | Model events only: the caller's model name and the `provider/id` OMP reports running. Names only, as OMP lists them; never free text |

Events:

- `idle` — the lane is ready for the next plan: native OMP idle, no pending messages, and no active bridge plan. Edge-triggered; sampled every 2 s (and once at enable) independent of the supervisor lane, so it is written within about 2 s of the change.
- `idle` with `reason` `bridge_stopped` — the bridge was turned off (or stopped itself on an error) while the lane was last reported `busy`; nothing samples the lane any more, so this closing edge keeps the watcher from staying `busy`.
- `busy` — the lane stopped being ready. `reason` is `native_busy`, `pending_messages` or `plan_active` (a bridge plan is in flight while native OMP appears idle).
- `plan_done` — a plan reached `completed`, `aborted` or `expired`, written when its receipt is saved. `completed` means every planned submission was admitted and ended; it never asserts that the work succeeded.
- `plan_done` with state `failed` or `malformed` — a plan that did not complete (reason says why, for example `end_not_matched_to_message` or `malformed_end`); `bridge_lanes_status` lists it as finished and needing attention. Rows written by older versions as `plan_unknown` / `unknown` read as `plan_done` / `failed`.
- `model_switched` — a controller `/model` request was proven: OMP itself reports the requested model running. `requested` is the caller's name and `model` is the `provider/id` OMP reports.
- `model_mismatch` — a `/model` request was not proven (OMP reports another model, or none). `requested` is the caller's name; `model` is what OMP reports running, absent when it reports nothing. Never read this as a switch that happened.
- `start_failed` — a lane start could not finish: the model was not proven (`model_unverified`) or the task was not confirmed stored (`prompt_not_delivered`, also when writing the queue failed at the disk). The task was not sent in the first case. Counts as needing attention until the lane reports something newer.

A plan that finishes normally produces `plan_done`, then `idle` on the next sample; the next queued plan is dispatched by the same 2 s timer, with no event needed. The polling period, not the event file, bounds dispatch latency; the file only makes completion and blockage machine-readable.

### Lane watcher files

The [lane watcher](lane-watch.md) is a reader of this feed, not part of it. It writes four more files beside `lane-events.jsonl` in the same private `control` folder: `lane-watch.log` and `lane-watch.log.1` (one line per change, at most 64 KiB each; the line format is in [lane-watch.md](lane-watch.md#line-format)), `lane-watch-state.json` (latest state) and `lane-watch-cursor.json` (last number shown to the coordinator); the owner's optional `lane-watch.json` configures it. They are content-free, never gate dispatch, admission or receipts, and are recognised and removed by uninstall.
